# 家庭本地智能体（Orion Smart Home）项目方案

> 本项目已作为一款可运行的全栈产品落地：**FastAPI + LangGraph** 后端与 **Vue 3 + Vite + TypeScript** 前端，实现了「自然语言 → 意图理解 → 工具调用 → 风险评估 → 执行」的完整 Agent 智能家居控制流程。本文档系统性地阐述项目起因、技术基础、场景价值、当前技术实现与后续所需支持。

---

## 一、项目起因

### 1.1 从「智能家居」走向「本地智能体」

随着智能音箱、智能照明、智能门锁、环境传感器和家庭机器人等设备快速普及，智能家居已经从单一设备控制逐渐发展为多设备协同。然而，目前主流智能家居系统仍主要依赖「App 操作 + 固定规则 + 云端服务」的交互模式，距离真正理解用户意图、主动完成复杂任务的智能家庭助手仍存在明显差距。

**首先，传统智能家居存在操作复杂、场景编排门槛高的问题。**
用户往往需要打开 App，在多个设备页面之间进行切换，并通过预先设置的「如果……那么……」规则实现自动化。例如，用户希望实现「晚上回家后自动打开客厅灯、关闭门锁提醒、调节空调温度并播放音乐」，传统系统通常要求用户提前创建多个自动化规则。对于普通家庭用户而言，这种方式不仅操作繁琐，而且要求用户理解设备之间的逻辑关系，难以适应自然、灵活的生活场景。

**其次，传统规则引擎具有明显的僵化特征。**
家庭环境和用户需求具有高度动态性，同一句自然语言指令可能对应不同的执行方案。例如用户说「我准备睡觉了」，系统需要结合当前时间、房间状态以及已有设备状态，判断是否关闭客厅灯、关闭电视、调低空调温度、检查门窗状态等。传统规则系统依赖人工枚举场景，很难处理这种具有上下文依赖和隐含意图的复杂任务。

大语言模型和智能体（Agent）的发展为解决上述问题提供了新的技术路径。大模型具备较强的自然语言理解、任务拆解和工具调用能力，可以将用户的一句话需求转化为多个具体的设备操作步骤。

因此，**大模型正在使智能家居从「用户操作设备」向「用户表达意图、智能体完成任务」转变。**

### 1.2 项目机遇：小模型与边缘计算使「家庭本地智能体」成为可能

虽然云端大模型能够提供较强的推理和规划能力，但直接将家庭智能体完全建立在云端服务之上仍存在三个核心问题。

**第一是数据隐私问题。**
智能家居系统涉及家庭成员、生活习惯、作息规律、设备状态甚至家庭活动等大量敏感信息。如果所有对话、设备状态和历史操作记录都上传至云端，用户需要承担较高的数据隐私风险。

**第二是网络依赖问题。**
云端智能体高度依赖互联网。当家庭网络异常、云服务不可用或者第三方 API 出现故障时，智能家居系统可能无法正常工作。而对于照明、门锁、空调等家庭设备而言，部分基础功能不应该完全依赖外部网络。

**第三是长期使用成本问题。**
如果智能体持续处理家庭成员的日常对话、设备状态和历史记忆，大量请求需要持续调用云端大模型 API。随着用户数量和使用时间增加，API 调用成本会持续累积，难以形成低成本、长期稳定运行的家庭智能系统。

与此同时，近年来端侧 AI 和轻量化大模型快速发展，模型量化、知识蒸馏、推理优化以及 NVIDIA Jetson 等边缘计算平台的发展，使得过去只能运行在数据中心的大模型逐渐具备了在本地设备运行的可能性。特别是 **1B 级别的小型语言模型已经能够在具备 GPU 加速能力的边缘设备上进行推理**，为家庭本地部署智能体提供了现实基础。

**「大模型能力 + Agent 自主规划 + 边缘计算设备」正在形成一个新的智能家居技术窗口，使智能体从云端走向家庭本地成为可能。**

### 1.3 我们的切入点：构建本地边缘部署的大模型智能体

基于上述背景，本项目选择从「本地边缘部署的大模型智能体」切入智能家居场景，目标不是简单地将一个聊天机器人部署到家庭设备，而是构建一个能够理解用户意图、调用家庭设备、进行任务规划、保存长期记忆并在本地持续运行的家庭智能体系统。

我们选择**本地边缘部署**作为项目的重要技术路线，主要基于以下考虑：

1. **数据不出家门。** 用户的对话内容、家庭设备状态以及长期记忆可以保存在本地，不需要持续上传到云端，从系统架构层面降低隐私泄露风险。
2. **断网仍然可以运行。** 大模型推理、Agent 规划、设备控制和历史记忆等核心功能均部署在家庭边缘设备上，即使互联网中断，也可以继续完成基本的智能家居控制。
3. **降低长期使用成本。** 传统云端方案需要持续支付模型 API 调用费用，而本地模型采用一次部署、持续使用的模式，在长期运行场景下可以显著降低边际使用成本。
4. **降低家庭智能系统对第三方服务的依赖。** 模型、Agent、记忆系统和设备控制逻辑均由本地系统掌握，可以避免由于第三方 API 调整、服务中断或者模型接口变化造成系统不可用。
5. **更适合家庭场景的实时交互。** 设备状态变化和用户指令可以直接在局域网内完成交互，减少云端通信带来的网络延迟，使智能体更加适合家庭自动化等需要快速响应的场景。

因此，本项目的核心理念并不是简单追求「更大的模型」，而是探索：

> **如何利用足够强的小模型和边缘算力，在有限计算资源下构建一个真正能够长期运行、保护用户隐私并具有自主任务规划能力的家庭智能体。**

## 二、工作基础

本项目并非从零开始，而是在已有大模型应用开发、智能体框架和边缘部署研究基础上进一步形成的系统化方案，且当前已具备一套可运行的全栈代码实现。

### 2.1 已具备完整的智能体软件开发基础

团队已经对当前主流 Agent 系统开发框架进行了实践，具备基于 **LangGraph** 构建智能体工作流的经验。能够将大模型的自然语言理解能力与工具调用、状态管理、任务规划等模块进行组合，实现带审批中断、风险分级与工具路由的多步骤任务执行。

在后端方面，团队熟悉 **FastAPI** 等 Python Web 服务框架，能够完成模型推理服务、Agent 服务以及智能家居设备 API 的封装，并实现不同模块之间的接口通信。同时掌握 **SQLAlchemy** ORM、**Pydantic** 校验与 **SSE（Server-Sent Events）** 流式输出技术。

在前端方面，团队具备 **Vue 3 + Vite + TypeScript** 开发经验，可以构建智能家居控制面板、设备状态展示、对话交互界面以及智能体运行状态监控界面，并基于 Pinia、Element Plus 与 Tailwind CSS 完成状态管理与界面搭建。

### 2.2 专为本地化模型做相应的适配与开发工作

在实际的大模型 Agent 使用过程中，随着对话不断增长，完整保存所有历史消息会导致上下文长度不断增加，从而带来显存占用增加、推理速度下降以及上下文成本增加等问题。团队研究了会话管理、上下文处理以及模型调用机制，并针对 MiniCPM 系列的 1B 级模型在本地部署时的长上下文问题做了专门适配。

针对这一问题，团队实现了一套新型的**会话树形存储与上下文压缩机制**，使系统能够在保留关键历史信息的同时，对冗长对话进行压缩、切分与迭代摘要，从而为家庭智能体实现长期运行和长期记忆提供基础。

这项工作对于本项目尤其重要，因为家庭智能体并不是一个「一问一答」的聊天机器人，而需要面对长期持续的用户交互。

因此，**会话存储、上下文压缩和长期记忆机制是本项目区别于普通大模型 Demo 的重要基础。**

### 2.3 已具备大模型与边缘部署方向的技术积累

团队持续关注轻量化大模型、模型量化以及边缘 AI 部署技术，对小参数量模型在有限算力环境中的推理能力进行了研究。

项目后续计划选择适合边缘设备部署的轻量化模型，并结合模型量化、KV Cache 优化等技术降低显存占用和推理成本，使大模型能够在 Jetson 等边缘计算平台上稳定运行。

相比单纯使用高性能服务器，本项目更加关注：有限算力下，大模型到底能否真正承担 Agent 的「决策中枢」角色。

这也是项目选择本地边缘部署的重要原因——不仅要验证「大模型能不能运行」，更要验证**「一个经过优化的小模型能否在真实家庭场景中完成有价值的智能体任务」**。

## 三、场景和价值

本项目面向家庭智能化、适老化和本地人工智能等实际需求，重点解决传统智能家居「设备多但交互复杂、自动化规则难配置、云端依赖强」等问题。通过在家庭边缘设备上部署轻量化大模型与智能体系统，使用户可以直接通过自然语言表达需求，由智能体理解意图、调用设备并完成多步骤任务。

### 3.1 面向场景

**日常设备自然语言控制。** 用户无需逐个打开设备 App，只需要通过自然语言表达需求，智能体可以识别其中包含的多个子任务，并按照预设的工具权限依次调用灯光、空调和窗帘设备，实现从「逐设备操作」向「统一意图控制」的转变。相比传统的按钮式控制，这种方式更加符合普通用户的自然交互习惯，尤其适合设备数量较多、操作频率较高的家庭环境。

**一键式复杂场景执行。** 对于「回家」「离家」「睡眠」「观影」「起床」等典型家庭场景，传统系统通常需要用户提前创建复杂的自动化规则。本项目可以将多个设备操作组合成一个由智能体统一执行的任务。智能体可以根据当前设备状态执行，并依据设备反馈动态调整任务，而不是简单执行一条固定脚本。

**自动化规则管理。** 传统智能家居自动化往往要求用户手动配置「触发条件—执行动作」。本项目可以利用大模型将自然语言需求转换为结构化自动化规则，例如**时间条件 + 人员状态条件 + 设备状态判断 + 执行动作**，从而降低自动化规则配置门槛，使不具备编程和智能家居配置经验的用户也能创建自己的家庭自动化场景。

**家庭设备状态查询与主动协助。** 智能体不仅可以执行控制指令，还可以作为统一的家庭状态查询入口。系统可以查询实时设备状态和历史操作记录，并通过自然语言进行回答。进一步地，在获得用户授权后，智能体还可以根据异常状态主动提醒用户，例如发现门窗未关闭、某设备长时间运行等情况。

**适老化与无障碍智能控制。** 对于老年人、行动不便人群以及不熟悉复杂智能设备操作的用户，传统 App 的多层菜单和设备配置存在较高使用门槛。本项目通过语音或自然语言交互，将复杂的设备操作转换成简单的语言指令。用户不需要理解设备型号、App 菜单和自动化规则，只需要表达自己的需求即可。因此，本项目不仅是对智能家居交互方式的升级，也具有一定的**适老化和无障碍应用价值**。

### 3.2 项目的核心价值

本项目区别于传统智能家居和纯云端大模型方案的关键，在于将**智能体的理解、规划、记忆和设备控制能力部署到家庭本地边缘设备**。

其价值主要体现在以下几个方面。

#### 隐私保护：家庭数据不必离开本地

家庭智能体产生的数据具有较强的私密性，包括用户对话、设备状态、家庭成员行为习惯、作息规律以及历史操作记录等。传统云端大模型方案通常需要将部分数据发送至远程服务器进行处理，而本项目将模型推理、Agent 运行、会话存储和设备状态管理尽可能部署在家庭本地。在不需要外部云服务的情况下，用户的核心家庭数据可以不离开家庭局域网，从系统架构层面降低数据外泄风险。

#### 离线可用：降低对互联网和云服务的依赖

家庭智能设备不应该完全依赖互联网才能完成基础功能。本项目将核心智能体能力部署到本地边缘设备，即使外部互联网暂时中断，只要家庭局域网和边缘设备正常运行，仍可以完成本地模型推理、设备状态查询以及部分智能控制任务。这使系统从**联网才能智能**进一步转向**本地即可智能，联网只是增强能力**，于网络环境不稳定、对实时控制要求较高的家庭场景具有实际意义。

#### 长期低成本：降低持续 API 调用费用

云端大模型通常按照调用次数、输入输出 Token 或计算资源进行计费。如果智能体每天持续处理家庭成员的对话、设备状态和历史记忆，长期使用会产生持续的 API 成本。本项目采用**一次边缘硬件投入 + 本地模型长期运行**的模式。虽然本地部署需要承担一定的硬件购置和维护成本，但对于长期运行的家庭智能体而言，可以减少甚至消除持续的大模型 API 调用费用，从而降低长期使用成本。需要指出的是，本项目并非宣称本地部署「绝对免费」，而是希望将成本结构从**持续按量付费**转变为**一次性硬件投入 + 较低的本地运行成本**。

#### 安全控制：智能体不是「想做什么就做什么」

大模型具有自主规划能力，但智能体直接控制门锁、电器等家庭设备也会带来新的安全问题。因此，本项目将**权限管理和风险审批机制**作为智能体系统的重要组成部分。可以根据设备风险等级划分操作权限：

- **低风险操作**：灯光、窗帘等，可直接执行；
- **中风险操作**：空调、电视等，可根据用户授权自动执行；
- **高风险操作**：门锁、燃气相关设备等，需要二次确认或明确授权。

这样可以在发挥 Agent 自主决策能力的同时，避免因模型理解错误导致危险操作。

#### 普惠化：降低智能家居使用门槛

传统智能家居的一个问题是「设备越来越智能，但使用越来越复杂」。用户需要学习不同设备 App、自动化规则、场景配置、设备参数以及多设备联动逻辑。

本项目试图将这些复杂操作隐藏在智能体内部，让用户只需要表达自己的需求。因此，其核心价值可以概括为：**让用户学习如何使用机器，转变为机器学习如何理解用户。**这对于老年人、儿童以及不熟悉智能设备的普通用户具有潜在普惠价值。

### 3.3 市场与技术发展背景

从技术发展趋势来看，智能家居正在经历从「单设备智能」向「多设备协同」和「自然语言交互」的转变。传统智能家居主要解决**设备联网 → App 控制 → 自动化规则**，而生成式人工智能和 Agent 技术进一步提供了**自然语言理解 → 任务规划 → 工具调用 → 多设备协同**的能力。与此同时，端侧 AI、模型量化和边缘计算技术不断发展，使得部分原本依赖云端的数据处理和模型推理逐渐可以下沉到本地设备。因此，未来家庭智能系统可能形成「**云端大模型 + 本地边缘小模型**」协同的技术架构：

- 本地小模型负责高频、低延迟、隐私敏感的家庭任务；
- 云端模型负责复杂推理、知识查询等本地模型难以完成的任务；
- 两者根据任务复杂度和隐私等级进行动态选择。

本项目首先聚焦于**本地智能体**，重点验证其在真实家庭设备控制场景中的可行性，为进一步构建云边协同的家庭智能系统提供基础。

| 对第三方服务依赖 | 较高      | 中等     | 高           | 低                  |
| 核心定位     | 设备控制工具  | 自动化工具  | 云端智能助手      | 家庭本地智能体            |

### 3.5 项目综合价值

综合来看，本项目的价值并不局限于「让智能家居能够聊天」，而是尝试建立一种新的家庭人机交互模式：**传统模式：用户学习设备 → 用户操作设备 → 用户配置规则**转变为**本项目模式：用户表达需求 → 本地智能体理解 → 智能体规划任务 → 设备自动执行**。其中，**本地边缘部署**是项目区别于普通云端 Agent 的核心特征。通过将大模型、Agent、记忆和设备控制能力下沉到家庭边缘设备，本项目能够同时兼顾**隐私保护、离线运行、长期低成本、低延迟和安全可控**等需求；通过自然语言交互和风险分级机制，又能够降低普通用户使用智能家居的技术门槛。最终，本项目希望推动智能家居从「**设备联网**」进一步走向「**家庭智能体化**」，使家庭中的大量智能设备不再是彼此独立的控制对象，而成为能够被统一理解、统一调度和安全管理的本地智能系统。

## 二、项目规划

### 2.1 整体目标

参赛期间，本项目的整体目标围绕「**在 Jetson 边缘设备上跑通一个安全、可长期对话的智能家居智能体**」这一核心任务展开，分「可展示原型」与「初步验证」两个层次，确保目标可衡量、可交付。

#### 可展示原型

在 NVIDIA Jetson 边缘设备上本地部署 MiniCPM 1B 级别模型，通过模型量化（INT4/INT8）与推理优化，使其在有限显存（4–8GB）环境下稳定运行，并实现以下完整功能链路：

- **自然语言控制家居设备**：用户通过自然语言指令直接控制灯光、空调、窗帘等设备，支持开关、调温、调亮度等操作；
- **场景执行与自动化规则管理**：一键执行预设场景（如「回家模式」「睡眠模式」），并支持通过自然语言创建、修改、启停自动化规则；
- **多轮对话与会话树形存储**：支持连续多轮对话，并基于会话树模型实现可分支、可恢复的长期记忆；
- **风险分级与审批机制**：对写操作进行风险分级，低风险自动执行，高风险 / 未知风险触发人工审批，审批带有效期并支持主动取消；
- **SSE 流式输出**：工具状态、模型回复、执行结果、审批请求通过 SSE 实时推送至前端，首次运行与审批恢复展示一致；
- **长对话上下文压缩**：上下文超限时自动触发摘要压缩，将关键历史信息回注模型上下文，确保边缘小模型也能「带着记忆」进行长对话。

以上所有功能均在 Jetson 本地完成推理与执行，无需依赖云端 API，实现数据不出家门、断网可用的核心目标。

#### 初步验证

在原型可运行的基础上，完成以下验证工作，产出可量化的评测结果：

- **功能评测**：在模拟设备环境 + 少量真实设备上，对智能体的指令解析、意图识别、工具调用、多轮对话、风险审批等核心功能进行系统性测试，验证各功能链路的正确性与稳定性；
- **安全评测**：对高风险操作的审批拦截、不可信数据隔离、写操作审计链、会话并发互斥等安全机制进行专项测试，确保高风险操作不可绕行、审批流程完整可追溯；
- **边缘推理性能评测**：在 Jetson 目标硬件上实测 MiniCPM 1B 模型的推理延迟（首 token 延迟与生成速度）、显存占用（模型加载 + KV cache）、吞吐量等关键指标，输出性能评测报告；
- **安全性评测报告**：汇总功能测试与安全测试结果，形成安全性评测报告，明确验证结论与潜在风险项。

通过以上原型搭建与验证工作，最终交付一套**可在 Jetson 上本地运行、功能完整、安全可控的家庭智能体原型系统**，以及配套的**边缘推理性能与安全性评测报告**，为后续真实家庭环境部署与行业落地提供技术依据。

## 四、当前技术实现

以下是本项目在当前代码库中已经落地并可以运行的核心技术实现，也是区别于普通大模型 Demo 的关键所在。整体采用**前后端分离**架构：后端为 `smarthome-api`（FastAPI + LangGraph），前端为 `smarthome-web`（Vue 3 + Vite + TypeScript）。

### 4.1 会话树形存储：把「对话」当作一棵可分支的树

与普通「消息列表」不同，本项目把一次对话建模为一棵 **append-only 的有向树**：任何分支（fork）、导航（move lane）、回滚与压缩，都是追加新节点、移动指针，**历史永不改写**。

- **可分支**：同一个对话可以从任意消息分叉出独立的实验分支，互不干扰；
- **可恢复**：每条写操作先落库、后应用内存，SQLite 事务 + WAL 保证崩溃一致性；加载时按 `seq` 重放；
- **可审计**：车道（Lane）记录操作生命周期（启动 / 中止 / 完成 / 重试 / 工具执行 / 用量），支持崩溃恢复与用量统计；
- **强不变式**：`SessionState` 集中校验「seq 连续、id 唯一、lane 存在、父节点链到车道叶子」等规则，配合 `walk_to_root` 环检测，坏数据被明确拒绝而非死循环。

会话树保存在 SQLite 中，将聊天会话（`ChatSession.id`）映射为树会话的 `session_key`，每轮用户消息与助手回复都会被镜像为树节点。

### 4.2 上下文压缩：让模型「带着记忆」进行长对话

LLM 上下文窗口有限，会话变长后必须把旧内容压成摘要才能继续工作。本项目实现了完整的上下文窗口管理，并**真正接入 Agent**（压缩摘要会回注模型上下文，而非只是存起来）：

- **触发判定**：阈值超限、上下文溢出、手动指令三种途径，含「消息被中止 / 模型已切换 / 已压缩过 / 无内容」等防御性跳过规则；
- **切割点算法**：从最新向最旧累积 token，**绝不切在工具结果上**；单轮超大时自动处理「split turn」；
- **双路径 token 估算**：优先用模型返回的真实 `usage`，兜底用 `chars/4` 启发式，即使持续收到错误响应，压缩仍可用；
- **迭代式摘要**：用「更新式提示词」把新消息并入旧摘要，而不是每次从零总结，历史信息不丢失；
- **分支摘要**：`/tree` 导航离开当前分支时，把被抛弃的分支压缩成摘要注入目标分支；
- **文件操作跟踪**：跨多次压缩累积 `read / edit / write` 清单，摘要后仍知道「动过哪些文件」。

### 4.3 LangGraph Agent 编排：安全可控的自动化

写操作不是「说执行就执行」，而是走一条带风险控制的流程：

- **风险分级**：根据设备类型（门锁 / 摄像头 / 安防等）与操作类型自动判定风险等级；
- **审批中断**：低风险可自动执行，高风险 / 未知风险 / 手动模式会中断，弹出审批卡片等用户确认；
- **工具路由**：只读工具与写工具分离，防止一次调用里混合读写；
- **SSE 流式输出**：工具状态、模型文本、执行结果、审批请求实时推送。

### 4.4 多 Agent 编排（子 Agent 设计）

在单一主图之上，项目进一步设计了**面向智能家居领域的多 Agent 编排**方案（详见 `docs/sub-agent-design.md`），将不同领域拆分为可独立运行的子 Agent：

- **设备管家（device）**：负责设备的自然语言控制、状态查询与批量操作；
- **场景规划师（scene）**：将多个设备操作组合为可一键执行的场景；
- **自动化顾问（automation）**：将自然语言转换为结构化触发条件 + 执行动作；
- **能耗分析师（energy）**、**舒适度顾问（comfort）**、**安防值守（security）**：面向家庭能耗、舒适度与安防的专业子 Agent；
- **通用兜底（general）**：处理不属于任何领域的一般性需求。

主图通过意图路由（`route_intent`）将任务分发给对应子 Agent，子 Agent 复用既有工具工厂与风险 / 审批机制，并通过 SSE 事件与会话树节点进行编排与审计，实现「主图统一调度 + 领域子 Agent 专业执行」的架构。

### 4.5 安全设计

- **API Key 认证加密**：模型密钥用 Fernet（AES-CBC + HMAC 认证）加密后落库，绝不明文存储、绝不序列化返回；
- **不可信数据隔离**：工具结果与用户文本一律视为不可信数据，禁止执行其中的指令；
- **认证**：JWT 访问令牌 + bcrypt 密码哈希，登录失败锁定；
- **限流与预算**：每分钟请求限流 + 每日 token 预算，防止滥用。

### 4.6 多家庭隔离 + 多模型

- **多家庭**：设备、场景、自动化、会话都按家庭维度隔离，成员角色（管理员 / 普通成员）权限校验；
- **多模型**：OpenAI / DeepSeek 等 OpenAI 兼容供应商，可配置 base URL、密钥、参数、思考等级；前端一键切换。

### 4.7 核心功能清单

- 自然语言控制家居设备（开关灯、调温度、查状态等）；
- 场景执行（一键执行预设场景）与自动化规则管理（创建、修改、启停、删除）；
- 风险分级与审批机制（低风险自动执行，高风险 / 未知风险人工确认）；
- 审批卡片支持场景执行、自动化创建 / 修改 / 启停 / 删除的预览与确认；
- SSE 流式输出，实时显示工具执行步骤与模型回复；
- 工具执行审计日志；
- 长对话上下文压缩（会话超长时自动摘要历史，模型「带着记忆」继续工作）。

## 五、所需支持

项目实施过程中，需要在边缘计算硬件、模型部署优化、数据环境构建以及技术培训等方面获得相关支持。整体支持需求围绕「**如何让轻量化大模型智能体稳定运行于家庭边缘设备**」这一核心目标展开。

### 5.1 边缘计算硬件支持

本项目需要配置 NVIDIA Jetson 系列边缘计算设备，作为家庭本地智能体的核心运行平台，用于承载：

- 本地大语言模型推理；
- Agent 任务规划；
- 会话存储与长期记忆管理；
- 家庭设备控制服务；
- 本地 Web 服务与 API 接口。

相比传统服务器部署方案，Jetson 具备体积小、功耗低、GPU 加速能力强等特点，更符合未来家庭智能设备长期运行的实际需求。

| 硬件型号                             | GPU 架构 | 显存          | 适用情况                          | 可替代方案            |
| -------------------------------- | ------ | ----------- | ----------------------------- | ---------------- |
| NVIDIA Jetson Orin Nano 8GB      | Ampere | 8GB LPDDR5  | 基础版本，适合 1B 级模型 INT4/INT8 量化推理 | Jetson Orin NX   |
| NVIDIA Jetson Orin NX 16GB       | Ampere | 16GB LPDDR5 | 推荐方案，可运行更大上下文、更稳定的 Agent 服务   | 工控机 + NVIDIA GPU |
| NVIDIA Jetson AGX Orin 32GB/64GB | Ampere | 32GB/64GB   | 面向复杂任务、多模型协同部署                | 小型服务器            |

综合项目成本、部署难度和模型规模考虑，本项目采用 **NVIDIA Jetson Orin NX 系列（8GB/16GB）作为主要边缘部署平台**。

原因如下：

1. MiniCPM 1B 级模型经过量化后可以在有限显存环境中稳定运行；
2. 8GB 显存能够同时支持模型推理、Agent 服务以及家庭设备管理服务，同时所需成本较低，16GB 版本可进一步承载更大的上下文窗口与更稳定的 Agent 服务；
3. 相比服务器方案，功耗更低，更接近未来家庭智能终端形态；
4. 为后续模型升级和多任务扩展预留一定空间。

### 5.2 大模型与推理优化支持

项目计划采用适合边缘部署的小参数语言模型作为智能体核心推理模型，使用 MiniCPM 系列 1B 级模型，该类模型具有参数规模小、推理速度快、中文理解能力较强等特点，更适合家庭边缘设备场景。

模型主要负责：

- 用户自然语言理解；
- 意图识别；
- 任务拆解；
- 工具调用决策；
- 简单上下文推理。

相比直接部署数十亿甚至百亿参数的大模型，1B 级模型能够在较低硬件成本下实现可接受的智能交互效果，更符合家庭设备长期运行需求。

### 5.3 后续优化方向

基于当前已落地的全栈实现，后续可进一步推进的方向包括：

- **模型本地化推理**：将从云端 OpenAI 兼容供应商切换为本地部署的轻量化模型（如 MiniCPM 1B），真正实现断网可用；
- **语音交互**：在前端对话基础上扩展语音输入与语音回复，进一步降低适老化和无障碍使用门槛；
- **前端驱动的 Agent 编排**：完善多 Agent 子任务的分发、追踪与可视化；
- **能耗与舒适度分析**：为「能耗分析师」「舒适度顾问」等子 Agent 补齐所需的数据采集工具。

## 六、总结

本项目从「智能家居走向本地智能体」的行业趋势出发，以**本地边缘部署 + 轻量化大模型 + Agent 自主规划**为核心技术路线，已在真实代码库中落地为一套可运行的全栈产品。项目通过**会话树形存储与上下文压缩**解决长时间对话的记忆与成本问题，通过**LangGraph Agent 工作流与风险分级审批**保障自动化操作的安全可控，并为多家庭、多模型与多 Agent 编排提供了可扩展架构。未来通过将模型推理下沉到 Jetson 等边缘设备并结合模型量化与优化，有望构建一个真正长期运行、保护隐私、离线可用且普惠的家庭本地智能体系统。
