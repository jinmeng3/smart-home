# Agent 现状审查与扩展路线

> 本文基于当前代码库的实际实现审查 agent 设计，不修改业务代码。
>
> 相关目标设计见 [10-langchain-agent.md](./10-langchain-agent.md)，当前聊天接口说明见 [08-ai-chat.md](./08-ai-chat.md)。本文优先以代码现状为准；当设计文档与代码不一致时，以“现状与差距”章节为准。
>
> 审查范围：`smarthome-api/app/agents`、聊天 API 与前端聊天状态流、模型配置、应用启动流程，以及 LangChain/LangGraph 接入方案。

---

## 1. 结论摘要

当前 agent 设计方向总体合理，但实现成熟度不足以支撑文档中描述的“可查询、可执行、可确认、可恢复”的智能家居 agent。

### 总体判断

- **分层方向合理**：将上下文、模型工厂、提示词、异常、检查点拆分，符合后续引入工具和 LangGraph 的演进方向。
- **安全目标正确但尚未闭环**：家庭隔离和风险确认已经进入设计与上下文对象，但目前主要依赖提示词或预留字段，尚未形成后端强制执行链路。
- **当前并不存在完整的 agent 运行链路**：代码中没有发现将 `AgentContext`、模型、工具、checkpointer 组装并运行的 agent service，也没有发现对应的确认决策 API。
- **规划文档与实现状态不一致**：`10-langchain-agent.md` 将很多目标能力写成设计方案，但 `08-ai-chat.md` 和前端代码仍对应普通聊天补全及固定执行步骤。
- **不建议直接继续堆工具**：应先完成最小闭环——可信上下文、只读工具、单个低风险执行工具、确认中断、幂等、SSE 事件和审计，再扩展自动化管理。

建议将当前阶段定义为：**Agent 基础设施预研 / 未上线**，而不是“agent 功能已完成”。

---

## 2. 当前实现盘点

| 模块 | 当前情况 | 判断 |
|---|---|---|
| `AgentContext` | 包含 `user_id`、`household_id`、`session_id` 和风险偏好，并校验家庭成员及会话归属 | 基础方向正确，但偏好语义存在安全问题 |
| system prompt | 注入家庭名称、设备数、高风险场景数，并声明家庭隔离及确认规则 | 只能约束模型，不能替代后端授权 |
| 模型工厂 | 仅实际构造 `ChatOpenAI`，却允许配置声明其他 provider | 实现与配置不一致 |
| 模型缓存 | 采用进程内 LRU，按模型 ID 和更新时间缓存 | 单实例可用，多实例和密钥轮换需补强 |
| checkpointer | 使用 SQLite `SqliteSaver`，全局单例，且启动流程未调用初始化函数 | 不能直接视为可用的生产持久化方案 |
| agent service | 未发现完整的 graph、tool binding、invoke/stream、恢复逻辑 | 核心缺失 |
| 工具层 | 未发现 agent 专用工具注册、工具参数约束和风险策略 | 核心缺失 |
| 确认流程 | 设计中有 interrupt 和 decisions API，但代码中未发现完整实现 | 核心缺失 |
| 后端聊天 API | 现有 `/api/chat/completions` 是普通模型转发协议 | 尚未接入 agent 协议 |
| 前端执行状态 | `useHomeChat` 创建固定四步并按文本流推进 | 不是实际工具执行状态 |
| SSE | 前端当前按 OpenAI `choices[].delta.content` 解析 | 与设计中的 `tool_started` 等 agent 事件不兼容 |
| 审计 | 现有业务服务可能有业务日志，但 agent 调用、参数、确认决策未形成独立审计契约 | 需要补齐 |

## 3. 设计中合理的部分

### 3.1 可信上下文独立于模型参数

`AgentContext` 将用户、家庭和会话信息放在后端构造，且设计上不允许模型覆盖，这是正确的信任边界。后续工具应该只从运行时上下文读取 `household_id`，不接受模型传入的 `user_id` 或家庭 ID。

### 3.2 工具复用业务 Service，而不是直接操作 ORM

`10-langchain-agent.md` 计划让工具适配现有 Service，这可以复用家庭归属校验、Schema 校验、事务和乐观锁，避免 agent 绕过业务规则。该原则应保留，并作为工具开发的硬性约束。

### 3.3 风险分级比统一确认更可用

将只读、低风险执行、高风险执行、配置变更和未知风险区分开，既能减少低风险操作的交互成本，也能保证门锁、摄像头和安防操作默认谨慎。未知风险按高风险处理也是合理的默认策略。

### 3.4 “已提交”与“已实际执行”分离

当前场景服务并不一定能证明设备已经完成物理动作，因此 agent 不应把服务返回的创建日志或 `running` 记录描述为设备已成功响应。这个约束对用户信任非常重要，应固化到工具返回模型和提示词中，而不是仅写在文档里。

### 3.5 将中断恢复纳入会话模型

使用会话 ID 关联 agent thread，并支持刷新页面后恢复待确认操作，方向正确。前提是 interrupt 必须有可验证的所有权、过期时间、一次性消费和审计记录。

## 4. 不合理或高风险的地方及建议

### 4.1 provider 配置白名单与模型工厂不一致

`Settings.supported_ai_providers` 默认包含 `openai`、`anthropic`、`cohere`、`gemini`、`deepseek`，但 `factory.py` 无论 provider 值是什么都构造 `ChatOpenAI`。这会导致：

- 非 OpenAI 兼容 provider 被错误地当成 OpenAI 使用；
- 配置通过 provider 校验，但运行时能力不匹配；
- 用户收到的错误与实际故障原因不一致。

**建议：**

1. 采用明确的 provider adapter 注册表，每个 provider 映射到独立的 LangChain ChatModel 构造器。
2. provider 枚举、依赖包、endpoint 是否必填、工具调用能力检查统一由工厂负责。
3. 在模型保存或测试连接时提前校验，不要等 agent 首次执行才失败。
4. 对 OpenAI-compatible provider 单独命名，例如 `openai_compatible`，不要把所有 provider 都伪装成 `openai`。
5. 支持的 provider 以实际安装和测试覆盖为准；未实现的 provider 不应出现在默认白名单中。

### 4.2 `AgentContext` 中的 `confirm_high_risk` 默认值存在语义漏洞

用户偏好存在且 JSON 合法时，代码使用 `ai.get("confirm_high_risk", False)`；这意味着缺少该字段时默认值为 `False`，而偏好不存在或 JSON 损坏时却默认 `True`。安全开关的缺省行为不应因“字段缺失”和“配置损坏”而变得更宽松。

**建议：**

- `confirm_high_risk` 默认始终为 `True`，并且该策略不可被普通用户偏好关闭，或至少关闭后仍需二次认证/管理员策略允许。
- 对偏好值做 Pydantic schema 校验，不直接信任 `dict.get` 的任意类型；例如字符串 `"false"` 不应被当作可靠布尔值。
- 将“用户偏好”和“系统/家庭安全策略”分层，最终风险策略取更严格者。
- 上下文中可保留偏好，但真正的风险判定必须由后端策略引擎执行。

### 4.3 只在 system prompt 声明家庭隔离不够

提示词中的“只访问当前家庭”不能防止模型产生错误参数，也不能防止工具实现缺少过滤条件。安全边界必须位于工具和 Service 层。

**建议：**

- 工具签名不暴露 `household_id`，从不可变运行时上下文注入。
- 每个工具调用前执行资源归属校验；查询、详情、写入、删除都必须覆盖。
- 禁止 agent 直接使用通用 SQL、HTTP、文件和 Python 执行工具。
- 对工具参数使用严格的 Pydantic schema：枚举、长度、范围、数量上限全部限制。
- 对跨家庭 ID、越权资源和未知风险统一返回结构化拒绝，而不是让模型自行解释。

### 4.4 checkpointer 实现存在资源和部署问题

`checkpointer.py` 中创建了一个未使用的 `sqlite3.connect`，随后又让 `SqliteSaver.from_conn_string` 自建连接；这可能造成资源泄漏和连接管理不清晰。函数名 `init_checkpoiter` 还有拼写错误，且 `main.py` 的 lifespan 没有调用它。代码注释和设计文档因此不能证明 checkpoint 已正确初始化。

此外，SQLite 文件型 checkpointer 不适合多进程、多实例部署；全局单例也没有明确的关闭生命周期。

**建议：**

1. 统一采用一个连接来源，明确连接的创建、setup、关闭责任。
2. 修正初始化函数命名，并在应用 lifespan 中显式初始化和关闭。
3. 为 checkpoint 增加 schema 版本、TTL/清理策略和并发测试。
4. 开发环境可使用 SQLite；生产环境优先使用 PostgreSQL checkpointer，并将 agent 状态与业务数据库部署策略分开评估。
5. 不要只以 `session_id` 作为 thread ID；建议组合 `user_id`、`household_id`、`session_id` 或在恢复时再次校验所有权，防止 ID 猜测和上下文串用。

### 4.5 模型缓存可能保留旧密钥和旧配置

当前缓存 key 依赖模型 ID 和 `updated_at`。如果时间戳没有可靠更新，或者密钥被外部密钥管理系统轮换而数据库记录未变，旧模型实例仍可能被复用。进程内缓存也无法在多 worker 间一致失效。

**建议：**

- 缓存 key 纳入配置版本，而不是依赖可空时间戳。
- API Key 不进入日志、异常消息、prompt 或 SSE。
- 更新/删除模型时主动失效对应缓存。
- 多 worker 场景使用短 TTL 或外部配置版本通知；不要把进程内缓存当作配置一致性机制。
- 对模型实例设置请求超时、最大输出和重试上限。

### 4.6 agent API 协议与既有聊天 API 冲突

`10-langchain-agent.md` 计划让 `/api/chat/completions` 运行 agent，但 `08-ai-chat.md` 仍将该接口定义为普通聊天转发，前端也按 OpenAI delta 格式解析。若直接替换，会影响已有客户端和前端。

**建议：**

- 短期新增明确的 agent API，例如 `/api/agent/runs` 和 `/api/agent/decisions`，保留普通 `/api/chat/completions` 的兼容语义。
- 或增加明确的请求能力字段/版本，但必须避免第三方客户端无意获得控制工具。
- 为 agent SSE 定义事件版本、事件 ID、重连游标和终止事件；不要让前端通过猜测文本判断执行阶段。
- 统一错误结构，区分模型错误、工具错误、权限拒绝、确认等待、超时和客户端取消。

### 4.7 确认机制不能只保存模型生成的 arguments

如果用户点击 approve 时后端直接执行 interrupt 中保存的参数，必须保证这些参数在等待期间没有失效，也没有被替换。对于 edit，不能让前端提交任意结构后绕过原工具 schema。

**建议：**

- interrupt 保存工具名、规范化参数、资源快照、风险级别、操作者、创建时间和策略版本。
- approve 时重新校验权限、资源归属、版本号、风险级别和参数 schema。
- edit 只允许修改白名单字段，并重新生成风险评估和确认摘要。
- 使用一次性状态转换：`pending -> approved/rejected/expired/executed`，数据库层防止重复消费。
- 为高风险动作增加短有效期；家庭成员权限变化后自动失效。

### 4.8 “自动执行低风险”不应只按场景标签判断

将一个 Scene 标记为 `high_risk` 是必要但可能不充分的。场景内容可能后续变化，或者一个看似普通的自动化包含门锁、摄像头、安防设备动作。

**建议：**

- 风险按实际动作展开计算，而不是只看场景静态标签。
- 风险计算器输出命中的规则、目标资源和原因，供确认卡片展示。
- 配置变更、批量操作、跨房间大范围操作、夜间/离家模式等可作为额外风险因子。
- 风险策略版本化，审计中记录判定版本，便于后续解释历史决策。

### 4.9 当前前端执行步骤会误导用户

`useHomeChat` 中的四步是固定文案，且收到文本 delta 后就推进状态；这不代表真实工具执行。用户可能看到“完成”但实际只有模型返回文本，或者看到“执行中”却没有任何后端执行。

**建议：**

- 改为基于结构化 SSE 事件创建步骤。
- 每个步骤展示 `call_id`、工具名称、开始/完成/失败时间和可读摘要。
- 客户端取消只表示停止读取，不应把已提交的写操作标为撤销。
- 加载会话时拉取待确认操作和运行状态，支持断线重连后按事件 ID 补齐。

### 4.10 缺少 agent 专用测试和可观测性

当前已发现的 agent 相关符号没有覆盖测试，安全关键逻辑不能依赖手工验证。没有完整的工具调用、确认、重试和断线场景测试时，不建议开放写工具。

**建议：**

至少补充：

- 家庭越权访问测试；
- 缺失/损坏偏好配置的默认安全测试；
- provider 与工具调用能力测试；
- 工具参数校验和未知风险降级测试；
- interrupt approve/edit/reject/expire/重复提交测试；
- 幂等键和并发提交测试；
- SSE 断线重连及客户端取消测试；
- 模型、工具和最终业务结果不一致时的错误处理测试。

观测方面应记录 trace/run/tool/call ID、耗时、状态、错误类别和 token/成本摘要，但对家庭名称、设备名称、地址、API Key 等敏感内容脱敏。

## 5. 推荐的落地顺序

### P0：先建立安全闭环

1. 明确 agent 与普通聊天的 API 边界。
2. 修正 `AgentContext` 的安全默认值和偏好 schema 校验。
3. 实现可信上下文注入及统一资源归属校验。
4. 统一 provider 注册表，删除未实现 provider 的默认声明。
5. 修复 checkpointer 初始化、连接生命周期和 thread 所有权校验。
6. 建立 agent 错误码、SSE 事件 schema 和审计事件 schema。

### P1：只读 agent

1. 实现 `list_rooms`、`list_devices`、`get_device`、`list_scenes` 等只读工具。
2. 对工具输出做最小化和脱敏。
3. 增加工具超时、最大迭代次数和单轮 token 限制。
4. 以真实工具事件驱动前端执行状态。
5. 先用测试模型/模拟模型验证 graph，不连接真实控制通道。

### P2：单个可控写操作

1. 选择一个低风险、可回滚或可验证的场景执行工具。
2. 实现后端风险计算和统一确认中断。
3. 加入幂等键、版本校验、一次性决策和审计。
4. 明确返回“已提交”“执行中”“已验证”“失败”四类状态。
5. 完成越权、重复提交、断线恢复和并发测试。

### P3：自动化管理

按 `create/update/set_enabled/delete` 分步开放，每个工具独立评估风险。创建和更新必须支持预览、影响分析、版本冲突和用户编辑后确认，不建议一次性开放全部管理工具。

### P4：生产化

1. PostgreSQL checkpointer 和多实例部署。
2. 外部密钥管理及 API Key 加密/轮换。
3. 超时、限流、成本预算和租户级配额。
4. 脱敏链路追踪、告警和运行回放。
5. 设备状态回读和实际执行验证。

## 6. 基于现有能力的扩展方向

以下扩展建立在当前家庭、房间、设备、场景、自动化、聊天会话和用户偏好能力之上，建议按价值和风险逐步推进。

### 6.1 只读家庭运维助手

- 全屋状态巡检：离线设备、异常状态、最近失败执行。
- 房间和设备自然语言检索。
- 场景预览：展示动作清单、影响范围和风险，不执行。
- 执行记录解释：按时间、设备和结果汇总异常。

这是最适合作为首个可上线能力的方向，因为可观测价值高、写入风险低。

### 6.2 可解释的场景执行

- 执行前展示将影响的设备和动作。
- 对普通灯光/空调等低风险操作提供用户配置的自动执行。
- 对安防、门锁、摄像头始终要求确认。
- 执行后根据业务日志或设备回读给出真实状态。

### 6.3 自动化设计工作台

- 从自然语言生成自动化草案，而不是直接写入。
- dry-run 和影响分析。
- 冲突检测，例如时间重叠、互相覆盖和循环触发。
- 根据历史执行记录提出节能或可靠性建议。
- 以结构化 diff 让用户确认修改内容。

### 6.4 家庭级策略与成员权限

- 家庭管理员设置高风险操作策略。
- 普通成员只能查询或执行指定低风险工具。
- 为儿童/访客账号提供更严格的工具白名单。
- 高风险操作可要求二次认证或管理员审批。

### 6.5 设备接入与状态验证

在接入 Home Assistant、MQTT、Matter 或 Zigbee 后，可将当前“已提交”扩展为：

`意图解析 -> 计划预览 -> 用户确认 -> 提交设备命令 -> 等待状态回读 -> 验证结果 -> 审计`

必须保留超时和未知状态，不能在没有回读证据时声称成功。

### 6.6 记忆与个性化

- 用户明确授权后保存语言、常用房间和偏好。
- 记忆必须可查看、修改、删除和导出。
- 家庭记忆与个人记忆分离，成员离开家庭时不共享个人数据。
- 记忆只用于建议和理解，不得绕过当前权限和确认策略。

### 6.7 动态模型路由

根据任务选择模型：只读查询使用低成本模型，复杂自动化规划使用更强模型，高风险工具调用使用经过能力验证的模型。路由结果、模型版本和工具能力应进入审计，避免出现不可解释的行为差异。

- [ ] 所有工具均从可信上下文获得用户和家庭信息
- [ ] 所有资源查询和写操作都有家庭归属校验
- [ ] 未知风险默认按高风险处理
- [ ] 高风险确认无法通过模型文本或前端绕过
- [ ] approve/edit/reject/expire/execute 是一次性、可审计的状态转换
- [ ] 写操作具备幂等键和并发控制
- [ ] checkpointer 已正确初始化、关闭，并验证多实例策略
- [ ] SSE 支持结构化事件、事件 ID 和断线恢复
- [ ] 前端不会把模型文本当作工具执行结果
- [ ] API Key、家庭敏感信息和内部堆栈不会进入模型或客户端
- [ ] 已覆盖越权、重复提交、超时、断线和异常恢复测试
- [ ] 业务结果能区分提交、执行、验证成功和失败

## 8. 需要在实现前明确的关键问题

1. agent 是仅服务当前登录用户，还是允许家庭管理员审批其他成员发起的操作？
2. 高风险操作是否允许关闭确认？如果允许，谁有权关闭，是否需要二次认证？
3. 设备控制的最终事实来源是现有业务日志，还是未来接入平台的状态回读？
4. 单个会话是否允许并行运行？如果不允许，如何处理重复请求和浏览器重试？
5. agent 的 checkpoint、审计和聊天消息分别保留多久，用户是否可以删除？
6. 多模型配置中的 API Key 是否迁移到加密存储或外部 Secret Manager？
7. 首个上线工具是否只读，还是需要一个可验证的低风险执行闭环？

这些问题会直接影响权限模型、数据模型、API 协议和上线风险，建议在实现 P0 前形成明确决策。
